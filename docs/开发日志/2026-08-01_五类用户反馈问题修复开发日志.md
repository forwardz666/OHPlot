# 2026-08-01 工作日志：五类用户反馈问题修复（统一根因：命令通道断裂）

> 用户反馈 5 类问题。根因分析后发现**大部分问题源于统一根因**：Qt 启动走了
> `qpa.startQtApplication` 成功路径，导致 qohos.cpp 的 `g_appHandle` 从未设置，
> ArkTS 覆盖层→Qt 的命令通道（callQtCommand/sendMouse）全部返回 "not ready"。

## 工作内容

1. **根因分析**（写入 `docs/下一阶段/2026-08-01_五类用户反馈问题根因分析.md`）：
   - **统一根因**：`g_appHandle` 只在 `startQtNative`（C++ 线程）里 dlopen 后设置（qohos.cpp:184）；
     `qpa.startQtApplication` 返回 true 时是独立 dlopen 实例，不设 g_appHandle → 命令通道全断
     → setChromeInsets/getUiState/sendMouse/menuAction 全返回 "not ready" → 顶部不对齐、
     新建矩阵失灵、表格交互失效、右键失灵全部由此引发。
   - 个别根因：问题2 的 `newMatrix()` 创建后未 addSubWindow/showNormal；问题4a 的
     ContextMenu @State 不传导父组件坐标；问题4b 的 ToolBar 无 onMouse；问题5 缺窗口控制键 UI。
2. **统一根因修复**：OHPlotAbility 改**无条件走 `qohos.startQtNative`**（C++ 线程），
   g_appHandle 被设置 → 命令通道恢复。
3. **问题2**：main.cpp menuAction `new_matrix` 分支补 addSubWindow/setFolder/addWindow/
   addListViewItem/showNormal/setFocus/modifiedProject（镜像 initMatrix）。
4. **问题3**：MainLayout `pushChromeInsets` 用 `getUIContext().vp2px()`（替代废弃全局 vp2px）。
5. **问题4a**：ContextMenu `@State positionX/Y` → `@Prop`（父组件坐标传导）。
6. **问题4b**：ToolBar 根 Flex 加 `.onMouse`（Right+Press → windowX/windowY 回调 → MainLayout 显示 ContextMenu）。
7. **问题5**：MainLayout 右上角新增 `—`/`□`/`✕` 窗口控制键（仅活动窗口时显示，走已有 menuAction 命令）。
8. **代码审查**：unspecified-high agent → 代码正确性全过；必须项（staging 未同步）已处理；
   建议项（setName 空操作、补 modifiedProject）已处置。
9. **构建部署 + 真机验证**：libentry.so 重建（含问题2 修复）→ HAP → 部署 → 验证。

## 技术决策

- **决策 1（统一根因）**: Qt 启动必须走 `startQtNative`（C++ 线程），禁用 `qpa.startQtApplication`
  作为启动路径。理由：qohos 的 g_appHandle（命令通道依赖）只在 startQtNative 里设置；
  startQtNative 复刻 startQtApplication 逻辑（setenv → dlopen → dlsym main → pthread），
  是 AGENTS.md 记录的原方案且 P0 验证报告确认可用。
- **决策 2（问题2）**: 在 main.cpp 命令层补显示逻辑（不动 libscidavis 库），镜像 initMatrix
  的 addSubWindow/showNormal 序列，最小侵入。
- **决策 3（问题4a）**: @State → @Prop（单向传导足够，@Link 双向非必需）。
- **决策 4（问题5）**: ArkTS 侧窗口控制键（借鉴 Windows 版布局），走已有 menuAction 命令，
  避免改 Qt MDI 标题栏。
