## 二、架构对比（详细）

### 2.1 Qt 启动方式

```
AirStars:
  MyAbilityStage.onCreate
    → qpa.attachAbilityStage(this)         // 早期 QPA 绑定
  EntryAbility.onWindowStageCreate
    → entry.preloadLibs()                   // dlopen 链式加载 Qt 依赖
    → entry.getQpa()                        // napi_load_module_with_info
    → qpa.startQtApplication(this)          // 平台插件内部 dlopen → main()
    → kstars_engine.cpp::main()
      → QApplication(argc, argv)
      → KStarsLite::createInstance()
      → app.exec()

scidavis-ohos:
  OHPlotAbility.onWindowStageCreate
    → initQtBridge()                        // 动态 import libQt5Core.so
    → qohos.startQtNative(dirs, lang)       // 自定义 C++ 线程
    → qt_thread_func()                      // pthread_create
      → setenv 环境变量
      → dlopen(libentry.so)
      → dlsym(main) → main()
        → QApplication(argc, argv)
        → app.exec()
```

**关键差异**：AirStars 使用官方 QPA 的 `startQtApplication`，平台插件内部管理线程和 dlopen；scidavis-ohos 因死锁问题完全绕过 QPA 的启动流程，自行管理线程和 dlopen。

### 2.2 XComponent 类型

| 项目 | 类型 | 说明 |
|------|------|------|
| AirStars | `XComponentType.NODE` | 官方 QPA 插件要求 NODE 类型 |
| scidavis-ohos | `XComponentType.SURFACE` | 与 NODE 兼容，但官方推荐 NODE |

`XComponentType.NODE` 虽被编译器标记为 deprecated，但当前 QPA 插件仍依赖此类型。AirStars 的开发日志明确记录了此问题，并计划在平台插件升级后迁移。

### 2.3 NAPI 桥接层对比

| 功能 | AirStars | scidavis-ohos |
|------|----------|----------------|
| **NAPI 导出函数** | 3 个：`preloadLibs` / `getQpa` / `isReady` | 4 个：`startQtNative` / `sendMouse` / `callQtCommand` / `onQtEvent` |
| **平台插件加载** | `napi_load_module_with_info(..., "com.airrdp.app/entry")` | 直接 `import 'libplugins_platforms_qopenharmony.so'` |
| **Qt 库加载** | 链式 `dlopen` (z→Core→Gui→Network→Xml→Widgets→kstarsengine) | 单一 `dlopen` (libentry.so) |
| **ArkTS→Qt 通信** | 无（QML 直接绑定到 C++ 对象） | `scidavis_call` JSON 命令通道 |
| **Qt→ArkTS 事件** | 无（QML 自带事件处理） | `threadsafe_function` + `EventSinkTrampoline` |
| **鼠标事件** | QPA 原生处理 | `scidavis_inject_mouse` + NAPI `sendMouse` |
| **JS 桥接对象** | 无 | 6 个：JsLocale/JsStandardPaths/JsInputMethod/JsCursor/JsPasteBoard/JsWindowManager |

## 三、可借鉴的关键实践

### 3.1 attachAbilityStage() 早期 QPA 绑定  ★★★

**AirStars 的做法**：在 `MyAbilityStage.onCreate` 中调用 `qpa.attachAbilityStage(this)`，在 Ability 创建前完成平台上下文绑定。

**scidavis-ohos 当前做法**：AGENTS.md 明确禁止在 AbilityStage 中导入 QPA，因为担心 NAPI 模块注册到错误的 `napi_env` 导致 SIGSEGV。

**建议**：重新评估此限制。AirStars 的成功实践表明，`attachAbilityStage` 是官方 QPA 插件设计的一等公民 API，正确使用时可以避免死锁问题。如果采用此模式，可以：
1. 消除自定义 C++ 线程 (`qt_thread_func`) 的复杂性
2. 使用官方 `startQtApplication` 替代手工 dlopen/dlsym
3. 减少约 200 行启动代码

**风险**：需在真机上验证，确保 `napi_env` 上下文正确。

### 3.2 nativeLib.collectAllLibs 简化库管理  ★★

在 `entry/build-profile.json5` 的 `buildOption` 中添加：
```json
"nativeLib": {
  "collectAllLibs": true
}
```

自动收集 `entry/libs/arm64-v8a/` 中所有 `.so` 打包到 HAP，无需手动管理每个库。配合 `abiFilters: ["arm64-v8a"]` 确保只打包目标架构。

### 3.3 HDS 设计系统集成  ★★

AirStars 的 `HdsVisualManager` 提供了完整的 HDS 视效管理：
- 设备能力探测 (`getSystemMaterialTypes`)
- 自适应材质等级 (`ADAPTIVE` / `SMOOTH`)
- 视觉特效工厂 (`pointLight` / `pressShadow` / `illuminatedContainer`)

可复用此模式，为 scidavis-ohos 的 ArkTS 覆盖层（菜单栏、工具栏、对话框）添加 HDS 视效，提升鸿蒙原生感。

### 3.4 交叉编译工具链脚本  ★

AirStars 的 `scripts/ohos.toolchain.cmake` 是一个可复用的 OHOS 交叉编译工具链配置，包含：
- `CMAKE_SYSTEM_NAME=OHOS`
- 正确的编译器、sysroot、目标 triple
- `CMAKE_FIND_ROOT_PATH_MODE` 策略
- 编译/链接标志

如果 scidavis-ohos 需要交叉编译 Qt 依赖库，可以直接复用此模板。

### 3.5 QML 插件预加载（未来参考） ★

如果 scidavis-ohos 未来考虑迁移到 QML 架构，AirStars 的 `kstars_engine.cpp` 提供了完整的 QML 插件管理方案：
- `patchQmldirPluginPaths()` — 修补 qmldir 中的插件路径为绝对路径
- `preloadQmlPlugins()` — 多轮预加载所有 QML 插件，处理依赖顺序
- 处理鸿蒙 `dlopen` 安全限制对 QML 插件加载的影响

## 四、scidavis-ohos 做得更好的方面（应保持）

1. **结构化链日志** (`SciDAVisChain`) — 跨 ArkTS/C++ 边界的关联 ID 追踪，定位问题效率远高于 AirStars 的分散日志
2. **ArkTS 覆盖层架构** — 完整的菜单栏/工具栏/对话框由 ArkTS 实现，更符合鸿蒙应用设计规范，用户体验更好
3. **Qt→ArkTS 事件通道** — `threadsafe_function` + `EventSinkTrampoline` 实现异步事件传递，架构设计更完备
4. **坐标转换** — 正确处理 vp→px 转换，适配不同屏幕密度
5. **中文 i18n 支持** — 语言标签映射 (`zh-Hans` → `zh_CN.UTF-8`) 比 `LC_ALL=C` 更适合中国用户
6. **剪贴板桥接** — 系统剪贴板 ↔ Qt 剪贴板双向同步
7. **项目文件管理** — 通过 `ohos.file.picker` 实现文件打开/保存

## 六、技术决策记录

### 决策 1：QPA 启动方式重构优先级

**选择**：高优先级，作为 Phase A。
**理由**：消除 200+ 行自定义线程管理代码，降低维护成本；与官方 QPA 插件设计对齐，减少未来升级阻力。
**约束**：必须在真机验证 `attachAbilityStage` 兼容性。如不兼容，保持当前方案并记录。

### 决策 2：保持 ArkTS 覆盖层架构

**选择**：不迁移到 QML。
**理由**：scidavis-ohos 的 ArkTS 覆盖层已经过完整验证，提供菜单栏、工具栏、对话框等完整 UI，用户体验优于纯 QML 渲染。AirStars 使用 QML 是因为 KStars 本身就是 QML 应用。

### 决策 3：保持自定义 NAPI 桥接

**选择**：保留 `sendMouse` / `callQtCommand` / `onQtEvent` 通道。
**理由**：QPA 插件不提供鼠标注入、JSON 命令通道和 Qt→ArkTS 事件通道。这些是 Widgets 应用在混合架构下的必需组件。
