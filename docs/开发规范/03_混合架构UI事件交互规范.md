# 混合架构 UI 事件交互规范

## 一、TouchEvent 无 `sourceType` 属性及安全转发方案

**问题现象：**
- ArkTS 编译报错：`Property 'sourceType' does not exist on type 'TouchEvent'`
- 鼠标左键在 Qt 界面中无响应

**根因分析：**
1. OpenHarmony 当前 SDK 版本中，`TouchEvent` 类型不支持 `sourceType` 属性
2. `TouchObject` 也不含该属性
3. ArkUI 将鼠标左键 Press/Release 转换为 touch 事件后，QPA 插件的 `touchDown` 函数为空实现，导致事件被静默丢弃

**正确修复方式：**
1. 在 `.onTouch` 中遍历 `event.changedTouches`（而非 `event.touches`）
2. 直接转发所有 Down/Up 事件为鼠标 Press/Release
3. **无需 `sourceType` 判断**，因为：
   - QPA 无双重分发风险
   - 手指触摸作为鼠标点击亦可接受

```typescript
.onTouch((event: TouchEvent) => {
    event.changedTouches.forEach((touch: TouchObject) => {
        if (touch.type === TouchType.Down) {
            this.sendMousePress(touch.x, touch.y);
        } else if (touch.type === TouchType.Up) {
            this.sendMouseRelease(touch.x, touch.y);
        }
    });
})
```

## 二、混合架构事件透传规范

**架构背景：** Qt C++ 后端 + ArkTS 前端混合界面。

### 2.1 问题描述
ArkTS UI 组件（如 `MainLayout`）若作为 `Stack` 顶层元素，默认会阻挡所有触摸事件，导致 Qt 后端无法接收点击。

### 2.2 正确做法
1. **事件转发内聚：** 将触摸事件转发逻辑（`onTouch` + `sendMouse`）内聚到 ArkTS 主布局组件内部
2. **透传设置：** 设置内容区域为 `HitTestMode.Transparent`，确保事件能透传至底层 XComponent
3. **子菜单处理：** 子菜单需支持外部点击自动关闭，避免遮挡和事件阻塞

### 2.3 实现要点
```typescript
Stack() {
    XComponent({ id: 'qtContent', type: 'surface' })
        .onLoad(() => { /* Qt 初始化 */ })

    Column() {
        // ArkTS 菜单/工具栏组件
    }
    .hitTestBehavior(HitTestMode.Transparent)  // 事件透传
    .onTouch((event: TouchEvent) => {
        // 转发事件到 Qt
    })
}
```

### 2.4 关键规则
- `HitTestMode.Transparent` 使组件自身不拦截事件但子组件仍可响应
- 确保 XComponent 尺寸正确覆盖内容区域
- ArkTS 层不应消费鼠标/触摸事件（除菜单交互场景）

## 三、mutation 命令队列化语义与未适配项拦截规范（2026-07-28 补充）

### 3.1 核心语义
`scidavis_call` 的命令分两类：
- **query 命令**（getUiState/getTableList 等）：同步等待 Qt 回答（3s 信号量兜底），返回真实结果；
- **mutation 命令**（menuAction/newTable 等）：队列化后**立即返回** `{"success":true,"queued":true}`，
  Qt 侧执行结果（包括 `unsupported` 错误）经 QueuedConnection 处理，**永远不会**出现在
  ETS 的同步返回值中。

### 3.2 强制规则
1. **禁止**依赖 mutation 命令返回值中的 `success===false` 做任何 UI 决策（该分支形同虚设）。
2. "功能是否已适配"属于能力协商，必须在 ETS 侧**前置判定**：维护与 C++ 命令注册表
   （main.cpp menuAction 白名单）**镜像同步**的 `MENU_ACTION_SUPPORTED` 常量数组，
   不在名单的 itemId 直接弹未适配对话框、不发 Qt。
3. C++ 侧白名单每次增删，ETS 镜像**必须同一提交内**同步修改，并在两处注释互相指向。

### 3.3 踩坑实录
未适配工具栏按钮点击后静默无响应：hilog 显示返回 queued:true，`resp.success===false`
的兜底 Toast 分支永不命中。真机自动化断言（弹窗轮询）暴露该缺陷。

## 四、浮动面板与顶部 chrome 带遮挡规范（2026-07-28 补充）

### 4.1 强制规则
1. 所有浮动面板（Results Log、ProjectTree 等 `position` 定位的 Column/Stack）的
   y 坐标**必须 ≥ TOP_CHROME_VP**（菜单栏 28 + 工具栏 32 = 60vp），禁止使用
   MENUBAR_HEIGHT_VP 作为面板起点——那会盖住工具栏带并**静默吞掉其全部点击**。
2. 顶部 chrome 常量（MENUBAR_HEIGHT_VP / TOP_CHROME_VP / STATUSBAR_HEIGHT_VP）每次
   调整后，必须全文检索所有 `position` 与事件守卫引用点同步更新。

### 4.2 定位方法论：uitest hit-test
点击"被吞"时，禁止猜测式排查，用 dumpLayout 全量 JSON 做坐标包含关系逐层打印：
对目标坐标 (x,y)，输出每个 bounds 包含该点的节点 type/bounds/enabled/clickable，
z 序最上层的可点击节点即拦截者。本项目实录：Plot 组按钮 (1969,96) 被
`Column [1277,79][2407,1039]`（Results Log 面板）拦截，据此锁定根因。

### 4.3 遮挡型缺陷的识别特征
- 脚本序列稳定失败而**手动单独操作全部正常**（脚本前序步骤留下了浮层）；
- 灰显类断言"通过"但实际处于遮挡之下（假阳性），须以 dumpLayout 的
  enabled/opacity 属性双重取证，不能只看"点击无反应"。
