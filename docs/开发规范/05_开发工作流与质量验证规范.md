# 开发工作流与质量验证规范

## 一、ArkTS 开发实践三原则

1. **即时编译验证：** 每完成一个组件必须立即编译验证
   ```bash
   hvigorw assembleHap --mode module -p product=default
   ```
2. **逐级提交：** 每完成一级必须 `git commit` + `git push` 到 GitHub
3. **忠实复现：** 所有 ArkTS 界面必须严格参照本地 Windows 版 SciDAVis 截图一比一复现，**禁止任何创新性设计**

---

## 二、分阶段开发与原子化提交规范

1. **分阶段推进：** 将修复任务划分为清晰的阶段，每个阶段完成后立即交付
2. **原子化提交：** 每个阶段完成后必须立即执行 `git add`、`commit`、`push`
3. **提交信息格式：** 严格遵循 `type(scope): description`
   ```
   fix(cpp): add scidavis_inject_mouse export for left-button injection
   feat(arkts): implement main menu layout with event forwarding
   refactor(qpa): clean up touch event handling
   ```
4. **远程同步：** 确保远程仓库实时反映最新进展，方便协作和回滚

**注意事项：**
- 禁止将多个不相关的修改混入同一个提交
- 提交信息必须能清晰表达本次变更的内容和目的

---

## 三、鸿蒙适配自主迭代修复工作流

### 3.1 闭环流程
每轮迭代执行以下标准化流程：

```
扫描问题 → 修复代码 → 重新构建 HAP 包 → 部署到真实平板设备
→ 运行完整测试套件 → 收集 hilog 日志 → 基于日志分析启动下一轮修复
```

循环终止条件：所有目标问题已达标，或达到最大尝试次数。

### 3.2 构建与部署命令
```powershell
# 构建
hvigorw assembleHap --mode module -p product=default --daemon

# 安装到真实设备
hdc install -r entry/build/default/outputs/default/entry-default-unsigned.hap

# 启动应用
hdc shell aa start -a EntryAbility -b com.scidavis.ohos

# 实时日志
hdc hilog -x | Select-Object -First 200
```

### 3.3 日志分析要点
- 过滤关键 TAG（如 `SciDAVis`、`QPA`、`Qt`）
- 关注崩溃堆栈（`cppcrash`、`js crash`）
- 记录每次修复前后的日志对比

---

## 四、真实设备验证要求

每次修复后必须在 **真实鸿蒙平板设备** 上完成以下四类强制验证：

| 验证维度 | 验证内容 | 通过标准 |
|---------|---------|---------|
| 启动与界面 | 应用启动、基础界面显示 | 无白屏/闪退，界面完整 |
| 输入响应 | 触摸及鼠标输入响应准确性 | 点击/滑动正确触发对应功能 |
| 长时间稳定性 | 持续运行 15+ 分钟 | 无内存泄漏/无渐进性卡顿 |
| 交互响应性 | 各类交互操作的响应性 | 菜单、对话框等操作无延迟 |

**禁止以下行为：**
- 仅使用模拟器验证，未在真实设备上测试
- 仅验证启动，未验证完整交互流程
- 发现问题不记录、不归因即继续开发

## 五、逐控件自动化回归脚本规范（2026-07-28 补充）

对工具栏/菜单这类多控件、有灰显契约的界面，除人工验证外应编写可复跑的自动化回归
脚本（本项目实例：tools/verify_toolbar.py，run6 达成 39/39 PASS）。

### 5.1 断言三支柱
| 支柱 | 手段 | 判定 |
|---|---|---|
| 行为分发 | 点击后 `hdc hilog` 抓关键字（如 `menu click: cut`） | 出现即 PASS |
| 弹窗/对话框 | 点击后 `uitest dumpLayout` 找目标文本（对话框标题、未适配文案） | 命中即 PASS |
| 灰显 | dumpLayout 读目标节点 `enabled`/`opacity` | 禁用态 enabled=false / opacity≈0.4 |

### 5.2 抗扰设计（缺一即产生误判）
1. **弹窗轮询**：对话框可能迟到，断言前轮询 3×1.2s，而非一次性 dump。
2. **失败清扫**：每个用例结束关闭残留对话框（点"确定/Cancel/取消"）与残留菜单
   （点空白区），防止"迟到弹窗污染"吃掉下一个用例的点击。
3. **下拉首击重试**：bindMenu 偶发首击被吞，open_dropdown 重试至多 3 次。
4. **浮层状态显式校验**：toggle 型面板（Results Log）用例后显式确认其真的关闭
   （见 03 规范遮挡条），盲双击 toggle 会因丢击奇偶错位而滞留浮层。
5. **状态相关断言的时序**：依赖前置状态的断言必须排在改变该状态的操作之前
   （例：undo/redo 灰显断言须在建表之前——建表即入 undo 栈）。

### 5.3 控制台编码
脚本输出含非 ASCII（✓/中文）时，Windows 控制台默认 GBK 会 UnicodeEncodeError，
运行前设 `$env:PYTHONIOENCODING='utf-8'`；结果统一 `Tee-Object` 落盘 `_vt_runN.log`
留档比对（过程日志本身不入库，见 GitHub 上传规范）。
